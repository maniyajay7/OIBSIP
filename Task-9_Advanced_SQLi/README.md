# Task 9: Exploit a Vulnerability in a Web Application (SQLi)

## 📌 Objective
To identify, demonstrate, and document an advanced SQL Injection (SQLi) vulnerability on a target web application—**OWASP Juice Shop**—by successfully bypassing administrative authentication via the login page.

---

## 🔧 What is SQL Injection (SQLi)?
SQL Injection is a critical web security vulnerability that allows an attacker to interfere with the queries an application makes to its database. By injecting malicious SQL code into input fields (such as login forms, search boxes, or headers), an attacker can force the database server to execute arbitrary commands. 

In this task, we perform a **SQLi Auth Bypass**, which manipulates the backend logic of the SQL statement to evaluate as true, letting us log in without credentials.

## 📡 The Vulnerability Mechanism (Under the Hood)

When a user submits credentials in the Juice Shop login page, the application executes a query dynamically constructing the database request:

```sql
SELECT * FROM Users WHERE email = '<USER_INPUT>' AND password = '<USER_PASSWORD>' AND deletedAt IS NULL;
```

If we inputs the following malicious string in the **Email** field:
```
admin@juice-sh.op'--
```
And any arbitrary string in the **Password** field, the compiled SQL statement executed by the database becomes:

```sql
SELECT * FROM Users WHERE email = 'admin@juice-sh.op'--' AND password = 'arbitrarypassword' AND deletedAt IS NULL;
```

### 🔍 Execution Analysis:
1. `admin@juice-sh.op'` closes the string literal for the email column.
2. `--` acts as a comment operator in SQLite.
3. Everything after the `--` (including the password verification and soft-delete checks) is treated as a comment and **entirely ignored** by the database compiler.
4. The database queries: `SELECT * FROM Users WHERE email = 'admin@juice-sh.op'`.
5. Since the default administrative email `admin@juice-sh.op` exists, the query successfully returns their record. The backend assumes authentication was successful and logs us in as the administrator.

## 🚨 Critical Security Consequences

If a web application is vulnerable to SQL Injection, the security consequences are devastating for an organization:

1. **Complete Authentication Bypass:** Attackers bypass credential checks entirely to log in as users, support staff, or administrators.
2. **Data Theft (PII & Credentials):** An attacker can extract the entire contents of database tables (emails, passwords, physical addresses, billing details, payment logs) via `UNION` queries.
3. **Database Modification & Deletion:** Attackers can run `INSERT`, `UPDATE`, or `DROP TABLE` statements to deface the site, manipulate orders, change prices, or destroy data.
4. **Server Takeover:** On certain databases (like MSSQL or PostgreSQL), functions like `xp_cmdshell` or copying files can allow attackers to run OS-level commands, leading to complete server compromise.
5. **Loss of Reputation & Compliance Fines:** Data breaches lead to direct violation of compliance frameworks (like GDPR, HIPAA, or PCI-DSS) resulting in heavy legal penalties and brand damage.

## 🛡️ Remediation: How to Secure the Code

To fix and prevent SQL Injection, developers must implement the following security engineering controls:

### 1. Parameterized Queries (Prepared Statements) - *Primary Defense*
Always separate code from data. By using prepared statements, the database compiler compiles the SQL query structure *before* inserting the user inputs. The inputs are guaranteed to be treated as literals, never as executable SQL statements.

* **Vulnerable NodeJS Code (Express/Sequelize):**
  ```javascript
  // Bad: Concatenating input directly
  sequelize.query("SELECT * FROM Users WHERE email = '" + req.body.email + "' AND password = '" + req.body.password + "'");
  ```

* **Secure NodeJS Code:**
  ```javascript
  // Good: Using Parameterized Queries
  sequelize.query('SELECT * FROM Users WHERE email = :email AND password = :password', {
    replacements: { email: req.body.email, password: req.body.password },
    type: QueryTypes.SELECT
  });
  ```

### 2. Input Validation and Sanitization (Defense-in-Depth)
* Use libraries (like `express-validator` or `joi`) to validate that input matches expected formats (e.g., verifying that the email field strictly conforms to an RFC-compliant email regex).
* Reject inputs containing known dangerous characters if they do not match the expected pattern.

### 3. Principle of Least Privilege
* Configure the database user account used by the web application to have only the minimum permissions necessary (e.g. read/write permissions only on specific tables; block execution of schema modification commands like `DROP` or administrative configurations).

### 4. Use Web Application Firewalls (WAF)
* Deploy a WAF (like AWS WAF, Cloudflare, or ModSecurity) to inspect HTTP requests for common SQL Injection payloads and block matching queries before they reach the web server.
